PRIORITY 5. GESTURES
Done August 12.

Fixed August 13. The robot used to repeat the same nod over and over

robot now does a noticeable alive gesture every ten seconds, either

HOW THE CODE IS BUILT, FOR STUDYING

Where the code lives. The robot runs from the folder
Supervaise-Reachy-Mini-Project-main in the home folder. The app code
is in its app subfolder. The web dashboard is separate, in the
pi_dashboard folder. A second folder ending in -develop holds the
research pipeline and is not what the robot runs.

The main files and what each one does, with their size in lines so
you know how big a read each is.

cj_voice_cloud.py, 1010 lines. The conductor. Owns the whole voice
loop: wake word listening, recording, the filler player, the stop
word, gestures, speaker gate, and it publishes everything the
dashboard shows. Start reading here.

cj_chat.py, 1481 lines. The brain. Loads the corpus and the voice
card, asks the router model which topic a question belongs to, then
asks the composer model to write the answer in his voice. Also
counts tokens and cache usage. The token budget lives here.

stream_speak.py, 343 lines. The mouth. Cuts the answer into
sentences as it is being written, turns each sentence into audio,
plays them one after another, tags each sentence with a feeling for
the gestures, and publishes the live captions.

voice_io.py, 640 lines. The ears and voice engine. Speech to text,
text to speech, the Filipino accent instructions, and the
pronunciation dictionary logic.

postprocess.py, 368 lines. The spelling fixer. Corrects misheard
Filipino names in the transcript using the entity dictionary.

dynamic_filler.py, 87 lines. Writes and voices the one sentence
filler that matches the question topic.

wake_word.py, 342 lines. The wake word detector wrapper.

speaker_id.py, 82 lines. The voice matcher for the speaker gate.

config.py, 781 lines. Every setting with its default and the
environment variable that overrides it.

dashboard.py, 1053 lines and supervaise_ui.py, 587 lines in
pi_dashboard. The web pages: troubleshooting page, audience page,
maintenance page.

How one question flows through the system, step by step.
1. wake_word hears Cee-Jap and cj_voice_cloud perks the robot.
2. The microphone records until you stop talking.
3. voice_io sends the recording to speech to text.
4. postprocess fixes misheard names in the transcript.
5. The question appears on the audience page.
6. A pre recorded filler clip starts playing at once, and
   dynamic_filler starts writing a topic filler in the background.
7. cj_chat asks the router which topic this is, picks the token
   budget for that theme, and starts the composer writing.
8. stream_speak takes each finished sentence, adds pronunciation
   help for hard Filipino words, makes audio, and plays it. First
   audio lands about nine seconds after you stop talking.
9. Each sentence updates the captions and sets the gesture feeling.
10. The full answer is saved for the replay button and the robot
    goes back to idle, doing an alive gesture every ten seconds.

How the parts talk to each other. The robot and the dashboard are
separate programs. They share small files in the memory only folder
called /dev/shm. The robot writes what it heard, what it answered,
what it is saying right now, wake word scores, and timing. The
dashboard reads those files and also writes small trigger files that
the robot checks, for the mute button and force listen and enroll.
These files vanish on reboot which is fine because they are live
state, not records.

Where settings live. Boot settings for the robot service are in
/etc/systemd/system/supervaise.service.d/wakeword.conf. Secrets and
a few caps are in app/.env. Defaults for everything are in
config.py. A setting in wakeword.conf wins over the default.

Suggested reading order for study. First read this file. Then read
the flow above while looking at cj_voice_cloud.py handle_turn and
wake_loop. Then cj_chat.py run_turn for routing and composing. Then
stream_speak.py for the sentence pipeline. The rest are helpers you
can read as they come up.


THE TOKEN SYSTEM AND TOTALS

What a token is. Models read and write text in pieces called
tokens. A token is about three quarters of an English word, so 100
tokens is roughly 75 words.

Which models are used. A small fast model called Haiku decides the
topic of each question and writes the topic filler. A larger model
called Sonnet writes the actual answer. Answers cost tokens two
ways: the prompt we send in, and the answer that comes out.

The answer budget. Each answer has a hard cap on how many tokens it
may write. Since August 11 the cap depends on the theme of the
question. The live numbers are:
Theme A legal doctrine 260
Theme B commentary and current events 240
Theme C biography and personal 200
Theme D foundation and mission 220
Theme E speeches and occasions 240
META questions about the robot itself 120

Why exactly those numbers. The base was 220, which came from
listening tests before August: at his slow speaking pace, about 220
tokens is roughly 165 words, which is about one minute of speech,
the right length for a kiosk answer. The themes then scale around
that base. Legal doctrine gets the most, 260, because citing a case
properly takes extra words. Biography gets 200 because anecdotes
are naturally compact. META gets 120 so identity questions get a
short graceful deflection, not a speech. These are first guesses by
design and can be tuned per theme with CJ_TOKEN_BUDGET_BY_DIM after
we watch real demo turns in the maintenance page turn table.

What one question costs in tokens, roughly. The prompt sent to the
composer is the big part: the voice card plus the retrieved corpus
passages, around five to nine thousand tokens per turn. Most of
that is identical every turn, so it is cached: cached tokens cost
one tenth of the normal price. The answer out is at most the budget
above. The router adds about a thousand tokens in and a few dozen
out per call.

Total tokens so far. The robot keeps its count in the system log,
and the log on this machine only reaches back to the current boot,
one in the morning of August 13. Since then the composer made 8
calls and processed 79760 tokens in total. The breakdown explains
the number: 42458 fresh prompt tokens plus 13587 tokens written
into the cache plus 22645 tokens read back cheaply from the cache,
and only 1070 tokens of actual answers out. In money that is about
twenty US cents. The number is input heavy because every answer
carries the whole persona and corpus context in with it, while the
budgets keep the spoken output small. That is the designed shape:
we pay pennies of mostly cached input to keep his voice and facts
right, and the caps keep both cost and answer length in check.

UPDATE 2026-08-19

Two new pieces landed on the develop checkout today.

1. Answer recheck gate (before the robot speaks). A zero-cost keyword
check now verifies every composed answer against a hand-edited list
of known facts (his appointment year, who appointed him, his birth
date, his column name, and a ban on any "I am an AI/robot" slip)
BEFORE text-to-speech. If a draft fails, the system recomposes once
with the correction spelled out; if it still fails, a safe fallback

enable it. The fact list is data/entities/answer_gate_rules.json —
edit it freely, changes load without a restart. Benchmark: 34 test
cases, catches 16/16 seeded errors, zero false alarms.

plays text in the cloned voice, EQ-tuned for the robot's small
speaker, with a local cache (repeat lines cost nothing and play
instantly) and a fallback ladder so the robot never goes silent —
canned clips for "connection lost / quota out / error" are already
rendered, and espeak-ng is installed as the very last resort.
Credentials live in voice/config.py which git ignores; the API key
must never be committed or pasted into logs. Live-tested against the
ElevenLabs API today; playback through the robot speaker not yet
exercised (the running service owns the speaker).
